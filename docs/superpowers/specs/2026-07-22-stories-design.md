# Сторисы (Instagram-подобные) — дизайн v1

- **Дата:** 2026-07-22
- **Статус:** дизайн согласован, реализация не начата
- **Затрагивает репозитории:** `jaidem_backend` (Django/DRF), `jaidem_student` (Flutter)
- **Точка входа в UI:** страница Жайдемчилер (`JaidemsPage`, первая вкладка нижней навигации)

## Цель

Дать жайдемчилер возможность публиковать эфемерные фото-сторисы и смотреть чужие — как в Instagram.
Точка входа — горизонтальная лента аватарок в верхней части страницы Жайдемчилер.

## Объём v1

Входит:

- только **фото** (без видео);
- автоистечение через **24 часа**;
- полноэкранный просмотрщик: полоски прогресса, автопереход, тап вперёд/назад, пауза по долгому нажатию;
- публиковать может **любой авторизованный жайдемчи**;
- у одного автора может быть **несколько** сторисов, в ленте он занимает одно кольцо;
- автор может удалить свой сторис; админ — через Django-админку;
- отметка «просмотрено» хранится **локально на устройстве**.

Не входит (сознательно отложено):

видео · текст и стикеры поверх фото · реакции · ответы в чат · highlights (закреплённые) ·
«кто посмотрел» и счётчики просмотров · жалобы и автоскрытие по N жалоб ·
синхронизация «просмотрено» между устройствами · пуш-уведомления о новых сторисах ·
изменения в админ-приложениях (`jaidem-admin`, `jaidem-admin-flutter`).

## Выбранная архитектура

**Вариант A — хранение в Django REST**, по образцу существующего `ForumPost`.

Рассмотренные альтернативы:

- **Firestore** — даёт реалтайм, но лишает модерации через Django-админку, раздваивает данные
  (автор в PostgreSQL, сторис в Firestore) и всё равно требует REST-эндпоинт для загрузки картинки.
- **Гибрид** (REST как источник правды + Firestore-сигнал о новом сторисе) — переусложнение для v1.

Реалтайм для сторисов некритичен: лента обновляется при открытии страницы и pull-to-refresh.
Взамен получаем единый источник данных и бесплатную модерацию через админку.

## Бэкенд (`jaidem_backend`)

### Модель

В `core/models.py`:

```python
class Story(models.Model):
    author = models.ForeignKey(Jaidemchiler, on_delete=models.CASCADE, related_name='stories')
    photo = models.TextField('Фото')          # URL, полученный от /category/image/
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        verbose_name = 'Сторис'
        verbose_name_plural = 'Сторисы'
        ordering = ['created_at']             # внутри автора — в порядке публикации
```

Отличие от `ForumPost`: там `author` объявлен как `SET_NULL`, здесь — **`CASCADE`**.
Лента группируется по автору, и сторис без автора отрисовать негде, поэтому при удалении
жайдемчи его сторисы удаляются вместе с ним.

`photo` — `TextField` с URL (а не `ImageField`), чтобы совпадать с тем, как хранятся
`ForumPost.photo` и `User.avatar`.

### Время жизни

Константа `STORY_TTL_HOURS = 24` — объявляется на уровне модуля в `core/models.py`
и импортируется во вьюсет, чтобы срок жизни был задан ровно в одном месте.

Истечение реализуется **фильтром на чтении** (`created_at > now() - STORY_TTL_HOURS`), а не
периодической задачей. Это всегда корректно и не требует инфраструктуры.
Физическую чистку просроченных строк и файлов можно добавить Celery-задачей позже —
Celery в проекте уже настроен. В v1 она не нужна.

### API

Один `StoryViewSet`, зарегистрированный по пути `/core/story/`
(в стиле существующего `/core/forum_post/`).

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/core/story/` | Лента активных сторисов, сгруппированных по автору |
| `POST` | `/core/story/` | Создать сторис |
| `DELETE` | `/core/story/{id}/` | Удалить свой сторис |

**`GET /core/story/`** возвращает уже сгруппированную структуру — UI рисует одно кольцо на автора,
поэтому группировка на сервере избавляет клиент от неё и уменьшает payload:

```json
[
  {
    "author": { "id": 12, "fullname": "Айбек", "avatar": "https://...", "isAdvisor": false },
    "stories": [
      { "id": 340, "photo": "https://...", "created_at": "2026-07-22T09:14:00Z" },
      { "id": 341, "photo": "https://...", "created_at": "2026-07-22T10:02:00Z" }
    ]
  }
]
```

Группы упорядочены по времени самого свежего сториса автора (новые выше).
Сторисы внутри группы — в порядке публикации.

Порядок с сервера — **только по свежести**: состояние «просмотрено» хранится на устройстве,
поэтому сервер про него не знает. Клиент затем перегруппировывает ленту по этому состоянию
(см. «Поток данных»), сохраняя внутри каждой группы серверный порядок по свежести.

**Пагинацию для этого вьюсета необходимо отключить** (`pagination_class = None`).
В `jaidem/settings.py` глобально задан `DEFAULT_PAGINATION_CLASS = PageNumberPagination`
с `PAGE_SIZE: 30`; без явного отключения он обернёт кастомный сгруппированный ответ
в `{count, next, previous, results}` и разобьёт ленту постранично.

**`POST /core/story/`** принимает `{"photo": "<url>"}`. Автор берётся из `request.user`, а **не**
из тела запроса — иначе можно было бы опубликовать сторис от чужого имени.

**`DELETE /core/story/{id}/`** разрешён только автору: `get_queryset` ограничивается
`Story.objects.filter(author_id=request.user.pk)`, поэтому чужой сторис вернёт 404.

### Права доступа

`IsAuthenticated` на все действия.

Существующие вьюсеты (например, `JaidemchilerViewSet`) стоят на `AllowAny`, но для сторисов так
нельзя: `request.user` нужен и для создания, и для проверки владельца.

### Загрузка фото

Новый эндпоинт **не создаётся**. Переиспользуется существующий `POST /category/image/`
(тот же, которым уже грузятся аватары в профиле): принимает multipart `{title, image}`,
возвращает `{"image": "<url>"}`. Полученный URL клиент кладёт в `photo` при создании сториса.

### Админка

`Story` регистрируется в `core/admin.py` (list_display: автор, дата, превью).
Это весь инструмент модерации для v1.

### Миграция

Нужна миграция, добавляющая таблицу `Story`.

Важно: в репозитории миграции уже отстают от моделей — файлы `user/migrations/` обрываются
на `0014`, хотя модель содержит более поздние поля. Поэтому миграция пишется **точечной**
(только `CreateModel` для `Story`), а применять её нужно в рабочем окружении:
`python manage.py migrate`.

## Приложение (`jaidem_student`)

### Модуль

Новый feature-модуль `lib/features/stories/` по той же clean-архитектуре, что `jaidems` и `forum`:

```
lib/features/stories/
├── data/
│   ├── datasources/stories_remote_data_source.dart (+ _impl)
│   ├── models/story_model.dart, story_group_model.dart
│   └── repositories/stories_repository_impl.dart
├── domain/
│   ├── entities/story_entity.dart, story_group_entity.dart
│   ├── repositories/stories_repository.dart
│   └── usecases/get_stories.dart, create_story.dart, delete_story.dart
├── presentation/
│   ├── cubit/stories_cubit.dart, stories_state.dart
│   ├── pages/story_viewer_page.dart
│   └── widgets/stories_strip.dart, story_avatar.dart, story_progress_bar.dart
└── stories_injection.dart
```

`storiesInjection()` вызывается из `initInjections()` в `lib/core/data/injection.dart`.
`StoriesCubit` добавляется в общий `MultiBlocProvider` в `lib/core/app/app.dart` —
как все остальные кубиты приложения.

### Виджеты

**`StoriesStrip`** — горизонтальная лента:

- первый элемент — «Твоя история» с плюсом, открывает `image_picker`;
- далее авторы: непросмотренные — кольцо градиентом `#3C2A98 → #FF854A`, просмотренные — серое;
- порядок: свои → непросмотренные → просмотренные.

**`StoryViewerPage`** — полноэкранный просмотрщик:

- полоски прогресса сверху, по одной на сторис автора, автопереход ~5 секунд;
- тап по правой половине — вперёд, по левой — назад; после последнего сториса автора —
  переход к следующему автору; после последнего автора — закрытие;
- свайп вниз или крестик — закрыть; долгое нажатие — пауза;
- шапка: аватар, имя, относительное время («2 ч назад»);
- на своём сторисе — кнопка удаления с диалогом подтверждения.

### Размещение на странице Жайдемчилер

`JaidemsPage` построена как `NestedScrollView`: `SliverAppBar` в `headerSliverBuilder`
и `BlocBuilder<JaidemsCubit>` в теле.

Лента добавляется как **`SliverToBoxAdapter` в `headerSliverBuilder`**, сразу после
`_buildSliverAppBar` — а не внутрь тела.

Обоснование: тело перерисовывается по состояниям `JaidemsLoading / JaidemsError / empty`.
Если положить ленту туда, она пропадала бы при ошибке загрузки участников и дублировалась бы
в трёх ветках билдера. В шапке она независима: **упал список участников — сторисы работают,
и наоборот.** При этом лента скроллится вместе с контентом, как в Instagram.

### Роутинг

`StoryViewerRoute` добавляется в `lib/core/routes/app_router.dart`.
Требуется прогон кодогенерации: `dart run build_runner build --delete-conflicting-outputs`.

### Отметка «просмотрено»

`SeenStoriesStore` — тонкая обёртка над `SharedPreferences`, хранит набор id просмотренных
сторисов.

Самоочистка: при каждой загрузке ленты сохранённый набор пересекается с id активных сторисов
и перезаписывается. Просроченные id отпадают сами, набор не растёт бесконечно.

### Локализация

Новые ключи добавляются во **все три** языковые мапы (`ky`, `ru`, `en`) в
`lib/core/localization/app_localizations.dart` — в этом приложении локализация сделана
ручными Dart-мапами, без ARB.

Ключи: `stories_your_story`, `stories_add`, `stories_delete`, `stories_delete_confirm`,
`stories_deleted`, `stories_upload_failed`, `stories_create_failed`.

### Попутная уборка

В `lib/features/profile/presentation/pages/profile_edit_form_page.dart` URL загрузки картинки
захардкожен строкой `https://jaidem-back.ru/jaidem/api/category/image/`.
Так как сторисы переиспользуют этот же эндпоинт, он выносится в `ApiConst.imageUpload`
и используется в обоих местах.

Также добавляется `ApiConst.stories = '/core/story/'`.

## Поток данных

1. **Открытие страницы Жайдемчилер** → `StoriesCubit.fetchFeed()` → `GET /core/story/` →
   клиент раскладывает группы по трём корзинам с учётом `SeenStoriesStore`:
   свои → непросмотренные → просмотренные. Внутри каждой корзины сохраняется серверный
   порядок по свежести. Группа считается просмотренной, только если просмотрены **все**
   сторисы автора.
2. **Создание** → тап «Твоя история» → `image_picker` (`maxWidth: 1080, imageQuality: 85`) →
   `POST /category/image/` (multipart) → получен URL → `POST /core/story/ {photo}` →
   перезагрузка ленты.
3. **Просмотр** → тап по аватару → `StoryViewerPage` со сторисами этого автора →
   каждый показанный сторис помечается просмотренным локально.
4. **Удаление** → на своём сторисе → подтверждение → `DELETE /core/story/{id}/` →
   перезагрузка ленты.

## Обработка ошибок

Ведущий принцип: сторисы — второстепенный контент и **не должны ломать страницу Жайдемчилер**.

| Ситуация | Поведение |
|---|---|
| Лента сторисов не загрузилась | Молча показывается только «Твоя история». Баннер ошибки не выводится, список участников не затрагивается |
| Не загрузилось фото | Тост с ошибкой, сторис не создаётся |
| Ошибка создания после успешной загрузки фото | Тост с ошибкой |
| Ошибка удаления | Тост, сторис остаётся в ленте |
| Лента пустая | Только кнопка «Твоя история», без большого empty-state |
| Оффлайн | Лента тихо пустая; при попытке создать — тост |
| Сторис истёк во время просмотра | Специально не обрабатывается: досматривается до конца, исчезнет при следующей загрузке ленты |

## Тестирование

В репозиториях сейчас нет тестовой инфраструктуры (`jaidem_backend/CLAUDE.md`: «no tests
implemented yet»), поэтому покрывается только логика, где реально можно ошибиться.

**Бэкенд** (`core/tests.py`) — три теста:

1. лента не отдаёт сторис старше `STORY_TTL_HOURS` (граница TTL);
2. `POST` проставляет автора из `request.user` — подмена автора через тело запроса не проходит;
3. `DELETE` чужого сториса возвращает отказ.

**Приложение:**

- `flutter analyze` без новых замечаний;
- один юнит-тест на чистую логику: сортировка групп (свои → непросмотренные → просмотренные)
  и самоочистка `SeenStoriesStore`;
- ручная проверка: публикация, просмотр, автопереход, удаление, поведение при ошибке загрузки ленты.

## Известные компромиссы

1. **Осиротевшие изображения.** Создание состоит из двух шагов (загрузка картинки, затем создание
   сториса). Если первый шаг прошёл, а второй упал, картинка остаётся на сервере без ссылки.
   У существующей загрузки аватара ровно та же особенность; ради v1 транзакционность не вводится.
2. **Отметка «просмотрено» только на устройстве.** После переустановки приложения или на другом
   телефоне все сторисы снова будут выглядеть непросмотренными. Осознанный размен ради отсутствия
   таблицы просмотров и запроса на каждый показ.
3. **Нет пагинации ленты.** За 24 часа объём сторисов ожидается небольшим. Если сообщество вырастет,
   потребуется пагинация или ограничение выборки.
